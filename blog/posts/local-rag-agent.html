Building a local RAG agent to explore a huge codebase

Nov 13, 2026 · 5 min read

Big open-source projects are great teachers, but they are hard to navigate. When I wanted to understand how a large Python framework organises its chat model integrations, I spent more time searching folders than learning. So I built a small agent to do the searching for me.

The goal

Ask questions in plain English, like "Where is the base class for chat models defined?", and get an answer that names the exact files it came from. And do it without sending a single line of code to an external API.

Why local?

In the sectors I have worked in, data often cannot leave the building. If AI is going to help there, it has to run on-premise. This project was my way of proving to myself that a useful setup fits on a normal developer machine.

The pipeline

  • Load: read the repository's source files.
  • Split: cut them into chunks that respect class and function boundaries.
  • Embed and store: turn each chunk into a vector and keep it in ChromaDB.
  • Retrieve: for each question, fetch the most relevant chunks.
  • Answer: a local model served by Ollama writes the answer and lists its sources.

Everything runs in Docker, so the whole stack starts with one command.

retriever = vectorstore.as_retriever(search_kwargs={"k": 5})
answer = chain.invoke({"question": question})
for doc in answer["sources"]:
    print(doc.metadata["source"])

What broke

The first version answered confidently and was sometimes wrong. Chunks that were too small lost the context of their class; chunks that were too big pushed useful code out of the prompt. Tuning chunk size and overlap mattered more than switching models.

Lesson: in RAG, retrieval quality decides answer quality. Fix the search before blaming the model.

Next steps

  • Add simple evaluation: a fixed set of questions with known answers.
  • Try hybrid search (keywords plus vectors) for exact class names.
